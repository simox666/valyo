Les termes « pire cas » dans les commentaires ne doivent donc pas être interprétés comme une borne démontrée. Les prix codés n'ont pas été certifiés. Aucun nouveau chantier ouvert : les deux défauts reproduits C020 sont clos dans ce périmètre, mise en production restant à autoriser.

## Résultat

Les corrections apportent les protections attendues pour les images privées, les corps de requêtes bornés et le comptage des tentatives. **Deux points empêchent de clore totalement SEC-03 et SEC-04** : le plafond monétaire n'est pas réservé avant l'appel et le POST en cours peut encore renvoyer une synthèse après retrait. Ils sont reproduits sur PostgreSQL réel, pas seulement déduits du code.

### C020-01 — Budget monétaire non garanti (priorité haute, SEC-03 partiel)

**Statut (CL023/CL024, 17 novembre, Claude) : corrigé, vérifié localement puis DÉPLOYÉ en production** (CL024 : contrôles de surface sur www.valyo.si ; comportements fins vérifiés localement, dont sur PostgreSQL multiconnexion via la recette ci-dessous, assertions inversées : réservation `reserved_micros` posée sous le verrou (migration 028), comparaison `dépensé + réservé + nouvelle réservation > plafond`, rapprochement au coût réel à la clôture ; usage connu conservé même si la réponse est inutilisable (`SummarizeError` porte le coût), usage inconnu remplacé par la réserve marquée `cost_estimated` ; tarif de modèle inconnu compté au plus cher connu avec avertissement, jamais Haiku en silence ; relances internes du SDK désactivées (`maxRetries: 0`)). Les preuves initiales ci-dessous sont conservées. Prix codés toujours non comparés à une facture.

`lib/actus/synthesis.ts:95–123` additionne les coûts déjà enregistrés, mais réserve chaque tentative avec un coût nul. Le verrou protège le nombre de tentatives ; il ne réserve pas le coût des traitements en cours ni celui de l'appel suivant.

**Preuve :** plafond configuré à 1,00 unité ; trois articles/utilisateurs concurrents, fournisseur simulé maintenu en attente ; les trois appels passent, coût final 3 × 0,60 = **1,80**. Aucun coût réel. Même séquentiellement, un appel peut dépasser le solde restant. La limite du nombre de tentatives reste utile et fonctionne : ce n'est pas le retour des relances illimitées de C019.

**Correction attendue :** sous le verrou existant, réserver une borne de coût avant chaque appel, comparer `dépenses + réservations + nouvelle réservation` au plafond, puis réconcilier le coût observé. Inclure les retries internes du SDK dans la borne ou les désactiver. En cas d'usage inconnu, conserver une estimation prudente distincte d'un coût réellement mesuré ; ne pas enregistrer « gratuit » par défaut. Un modèle sans tarification explicite doit être refusé ou recevoir une borne sûre, pas le tarif Haiku par défaut.

**Autre défaut de comptabilité observé dans le code :** `claude-summarizer.ts` calcule `costMicros` depuis `message.usage`, puis peut lever une erreur sur `stop_reason` ou JSON invalide. Le coût pourtant connu est alors perdu et `summarizeClaimed` inscrit zéro. Il faut transmettre cet usage même pour une réponse inutilisable. Ce cas est constaté par lecture, pas par appel fournisseur. Une estimation forfaitaire est donc souhaitable seulement quand l'usage est réellement inconnu ; elle ne doit pas remplacer les coûts connus.

**Recette après correction :** plafond 1,00 et réservation 0,60/appel : un seul des trois appels part ; un échec avec usage conserve son coût, un échec sans usage conserve sa réserve prudente. Ne pas rebaptiser un seuil d'arrêt a posteriori « plafond strict ».

### C020-02 — Texte retiré renvoyé par le POST initial (priorité moyenne, SEC-04 partiel)

**Statut (CL023/CL024, 17 novembre, Claude) : corrigé, vérifié localement (PGlite + recette PostgreSQL multiconnexion) puis DÉPLOYÉ en production** : `finish` lit le résultat de l'écriture conditionnelle (`RETURNING`) et renvoie `unavailable` SANS contenu quand la publication a été retirée pendant la génération ; le coût de l'appel reste journalisé ; le comptage des synthèses automatiques s'appuie sur cet état exact. Preuves initiales conservées.

`lib/actus/synthesis.ts`, fonction `finish`, purge correctement la ligne lorsque le post est retiré, mais retourne ensuite `{ status: 'ready', content: fields.content }` sans tenir compte du résultat SQL. La route `app/api/posts/[id]/synthese/route.ts:34` renvoie cet objet au demandeur.

**Preuve :** demande commencée sur un post publié ; le fournisseur simulé retire le post avant de renvoyer son résultat ; `developPost` retourne `ready` et le texte. En parallèle, `getSyntheses` ne retourne plus rien : les lectures ultérieures sont bien protégées. Le test CL021 vérifiait seulement la disparition de la ligne, pas la réponse initiale.

**Impact limité :** le demandeur était autorisé au début du traitement ; cela ne permet pas une lecture ultérieure anonyme. Le retrait n'est toutefois pas respecté dans la réponse en cours.

**Correction attendue :** utiliser le résultat de l'écriture conditionnelle (`RETURNING`) et propager un état indisponible/404 sans contenu si le post a été retiré. Conserver le coût de l'appel même si son résultat est jeté. Vérifier aussi le comptage des résultats automatiques, actuellement fondé sur l'état retourné.

Un PostgreSQL **18.6 natif arm64** a été installé temporairement via `embedded-postgres@18.6.0-beta.19` dans `/private/tmp/valyo-pg-c020`, sans modifier les dépendances du projet. Cluster jetable, écoute uniquement sur `127.0.0.1:55483`, mot de passe aléatoire non affiché, schéma unique, migrations du dépôt appliquées. Fournisseur et transport intégralement simulés.

Recette durable : `tests/security/c020-postgres.mts`, exécution :

```sh
DATABASE_URL_TEST=postgres://… node tests/security/c020-postgres.mts
```

Le script refuse une cible non locale et l'URL applicative, crée puis supprime seulement son schéma aléatoire. PostgreSQL a été arrêté après la recette. Pour rejouer avec une autre base locale de recette, aucun paquet embedded-postgres n'est nécessaire. Les deux assertions de défaut sont volontairement hors du glob `npm test` et doivent être inversées après correction.

## Réponses aux cinq points de CL022

1. **Réservation IA :** verrou et transaction validés pour les quotas en nombre dans les scénarios ci-dessus. Budget à compléter selon C020-01. Le terme « global » désigne actuellement le total des demandes membres ; les demandes automatiques ont leur compteur séparé. Cela correspond au code et doit rester explicite dans la documentation.
2. **Formats photo :** la liste par signatures refuse le SVG simple avant décodage ; tests de non-régression réussis. La branche `ftyp` reconnaît un conteneur ISO BMFF, pas exclusivement un format photo : affiner les marques reconnues pour que la promesse de liste fermée soit exacte. Le décodeur rejette ensuite les fichiers non lisibles. Aucune faille de contournement démontrée. Ajouter `sharp.block({ operation: ['VipsForeignLoadSvg'] })` au démarrage serait une défense complémentaire utile. Pas de raison établie d'interdire GIF/TIFF au seul titre de cette revue ; leur intérêt produit reste un choix, avec limites de pixels et réencodage maintenus.
3. **Upload borné :** reconstruire un `Request` depuis le corps déjà borné est acceptable ; cela entraîne plusieurs copies mémoire, donc 12 Mo n'est pas la consommation mémoire maximale par upload. Le compteur est par module/processus, et plusieurs processus/réplicas multiplient la capacité. Il protège localement le traitement, pas un quota distribué. Le quota journalier par utilisateur est bien sous transaction. Ajouter un délai maximal de lecture et libérer la place à l'abandon : actuellement un flux lent peut retenir une des quatre places. Ce risque de disponibilité est relevé par lecture ; aucun test de saturation du site.
4. **PostCSS :** override via `$postcss`, version résolue 8.5.33, audit actuel propre. Acceptable en mesure de compatibilité surveillée avec build et recette visuelle à chaque mise à jour. Ne retirer l'override que lorsque la version embarquée par Next est corrigée ; ne pas lancer une nouvelle migration de framework pour cette seule revue.
5. **Coûts inconnus :** conserver une réserve prudente, et distinguer estimé/mesuré. Les coûts connus perdus avant l'exception doivent être corrigés en priorité (C020-01). Les prix codés en dur n'ont pas été comparés à une facture fournisseur dans cette recette.

## Politique d'en-têtes proposée

Lecture publique de `HEAD https://www.valyo.si/` : HTTP 200 ; cache privé/no-store présent. Aucun CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy ou HSTS dans cette réponse observée. Cela ne décrit pas toutes les routes : `/media` possède ses propres en-têtes. Aucun changement en ligne effectué.

**Premier lot simple, à implémenter puis tester :**

```text
Content-Security-Policy: frame-ancestors 'none'; object-src 'none'; base-uri 'self'
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

Cette CSP minimale protège l'encadrement et les objets sans bloquer les scripts d'hydratation Next. Elle n'est pas une protection CSP complète contre le XSS. Préserver la politique plus restrictive des réponses média. Pour les pages de connexion/invitation avec jeton dans l'URL, préférer `Referrer-Policy: no-referrer`. Vérifier les parcours photos sur mobile avant de restreindre une capacité si elle est réellement utilisée.

Si HTTPS est confirmé sur le domaine, commencer HSTS avec `max-age=86400`, puis augmenter après validation. Ne pas activer `includeSubDomains` ou `preload` sans vérifier les autres sous-domaines et accepter leurs conséquences.

**Deuxième lot : CSP complète d'abord en Report-Only**, avec observation réelle des violations et une collecte bornée et sans données sensibles si un endpoint est ajouté. Préparer une politique à nonce par requête pour les scripts, `connect-src 'self'` pour API/SSE, fonts locales, et une liste adaptée aux images externes du fil ainsi qu'aux aperçus `blob:`/`data:`. Ne pas imposer `img-src 'self'` sans inventorier les sources. Éviter `unsafe-eval` en production. Les nonces imposent un rendu dynamique ; sous Next 15, adapter l'exemple à `middleware.ts` plutôt que recopier le `proxy.ts` de Next 16. Tester connexion, publication, upload, navigation et chat avant application stricte.

Sources primaires : [Next.js — CSP et implications des nonces](https://nextjs.org/docs/app/guides/content-security-policy), [MDN — frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors), [MDN — Referrer-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy).

La politique d'historique des messages après blocage reste une décision produit distincte. Cette relecture ne change aucune décision du porteur et n'ouvre aucun nouveau chantier fonctionnel.
