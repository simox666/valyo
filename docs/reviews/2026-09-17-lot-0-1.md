# Audit Lot 0 et revue Lot 1 — Codex

Date : 17 septembre 2026. État courant sans Git ; références de lignes relevées pendant la revue. Aucun code applicatif modifié, aucune clé lue, aucun appel IA réel lancé. Les tests chargent les modules TypeScript isolément et remplacent la frontière vision ; ce ne sont pas des tests HTTP de bout en bout.

**Verdict : audit Lot 0 terminé ; Lot 1 = corrections demandées.** Le build réussi ne valide ni le comportement mobile ni la qualité des prix. Les tests manuels décrits par Claude Code sont conservés comme résultats rapportés, non reproduits ici.

## Constats prioritaires

### R1 — P1 : prix publiables sans preuve et fourchettes invalides

Références : `lib/schema.ts:47–53`, `lib/prompts.ts:6`, `lib/vision.ts:73–85`, `components/ResultCard.tsx:53–56`.

Reproduction : tests « rejects a priced result without evidence » et « rejects negative and reversed price ranges ». Un objet avec zéro source et une estimation 100–200 EUR est accepté ; une fourchette 200 à -1 aussi. Le prompt hors périmètre demande une fourchette approximative et le résultat du modèle est directement affiché. Ce constat démontre l'absence de garde-fou, pas qu'un appel réel inventera systématiquement un prix.

Attendu : contrôler les invariants métier après extraction, autoriser des valeurs nulles, interdire valeurs négatives/fourchettes inversées et ne publier aucun montant sans preuve admissible. Séparer identification, preuves et calcul ; préserver les références structurées et dates plutôt que seulement un résumé textuel. La présence d'une URL seule ne suffira pas à valider la preuve au Lot 2.

### R2 — P1 : écran encore conforme à l'ancien produit

Références : `components/ResultCard.tsx:60–84`, `lib/schema.ts:47–52`, `lib/prompts.ts:23`.

Lecture : « Prix conseillé », « Vente rapide » et pourcentages de confiance sont toujours affichés. `retail_price_new` est collecté mais jamais rendu. Les valeurs nulles produisent « — – — » sans état explicite de prix indisponible.

Attendu : retirer les sorties liées à la vente et les pourcentages non calibrés ; afficher neuf/occasion distinctement lorsque disponibles et un message explicite sinon. Revoir aussi les champs et prompts pour éviter de payer pour des résultats hors périmètre. La classification par enum est une amélioration structurelle, mais ne prouve pas la classification correcte des sources.

### R3 — P1 avant ouverture publique : appels coûteux sans contrôle d'accès ni quota

Références : `app/api/analyze/route.ts:16–45`, `lib/vision.ts:46–79`.

Lecture : tout client peut lancer l'analyse sans limite d'usage serveur. La limite de deux photos est par requête et ne borne pas le nombre de requêtes. Jusqu'à cinq appels de recherche de reprise puis une extraction sont prévus ; le budget global n'est pas mesuré. Les limites déclarées de recherche par appel ne constituent pas un plafond monétaire par utilisateur.

Attendu : protection adaptée au pilote (accès limité, quotas serveur, plafond global), coûts/usage par tentative, timeout et stratégie de retry explicites. Conserver le développement local possible ; ne pas ouvrir à 100 utilisateurs avant ces contrôles et une décision de budget. Aucun abus réel n'a été tenté.

### R4 — P2 : requêtes malformées insuffisamment validées

Références : `app/api/analyze/route.ts:19–38`.

Reproduction : JSON `null` lève un TypeError hors du bloc d'erreur fournisseur ; la chaîne « not an image! » avec MIME JPEG atteint le fournisseur simulé et reçoit 200 dans le test. Le type TypeScript du body n'effectue aucune validation runtime.

Attendu : schéma de requête, réponse 400 pour null et types incorrects, validation base64 et format réel, taille globale bornée avant traitement coûteux. Ne pas faire confiance au MIME déclaré ni au redimensionnement client. Tester les limites sans envoyer de charge importante au fournisseur.

### R5 — P2 : liens de sources non validés

Références : `lib/schema.ts:23`, `components/ResultCard.tsx:111`.

Reproduction : le schéma accepte `javascript:alert(1)` comme URL. Il s'agit d'un défaut de contrat ; aucune exécution JavaScript dans React n'est alléguée ou testée.

Attendu : URL absolue HTTP(S) uniquement, rejet des autres protocoles et présentation sûre. Une URL syntaxiquement correcte ne garantit pas sa provenance.

### R6 — P2 : correction manuelle et reprise incomplètes

Références : `app/scan/page.tsx:48–103`, `app/scan/page.tsx:135–153`.

Lecture : aucun formulaire de correction ou possibilité de passer la relance ; « Réessayer » efface les deux photos, y compris après une erreur transitoire au second tour. Le décodage est lancé avant de désactiver l'import : deux sélections rapprochées peuvent lancer plusieurs opérations et leurs résultats ne sont pas protégés contre une arrivée dans le désordre. Aucun AbortController/identifiant de requête, délai client ou annulation n'est présent.

Attendu : état de préparation immédiatement verrouillé, correction/transmission des informations utilisateur, possibilité de résultat partiel, relance sans reperdre les photos et protection contre les réponses périmées. Ajouter des tests navigateur avec réponses simulées retardées. Risque de course identifié par lecture, non reproduit dans un navigateur pendant cet audit.

### R7 — P2 : durée prévue incompatible avec les mesures rapportées

Références : `app/api/analyze/route.ts:7`, `app/scan/page.tsx:14–18`, `lib/vision.ts:46–79`.

La route déclare 60 secondes, alors que le passage de relais rapporte des scans de 59–80 secondes et davantage. Sur un hébergement appliquant cette durée, ces scans risquent d'être interrompus ; le succès local ne le vérifie pas. Le message « presque fini » est seulement piloté par un chronomètre, sans connaissance de l'avancement.

Attendu : aligner budget de temps et hébergement, interrompre proprement les appels, mesurer identification/recherche/extraction et choisir une reprise ou un traitement différé si nécessaire. Remplacer la promesse de fin imminente par un message honnête. Pas de déploiement réalisé ici.

### R8 — P2 : journalisation sans contrat et libération des images

Références : `app/api/event/route.ts:7–8`, `app/api/analyze/route.ts:48`, `app/scan/page.tsx:61,96–100`, `lib/image.ts:42`.

Lecture : `/api/event` journalise tout JSON reçu ; aucun filtrage n'empêche un client d'y envoyer des données sensibles. Les erreurs fournisseur sont loguées intégralement ; leur contenu doit être vérifié et réduit. Les URL d'aperçu ne sont jamais révoquées et les ImageBitmap ne sont pas explicitement fermés : risques de rétention mémoire lors de scans répétés. L'aperçu utilise l'original HEIC même si le pipeline l'a converti : il peut rester illisible dans le navigateur qui a nécessité la conversion.

Attendu : liste fermée d'événements/champs, taille bornée, erreurs expurgées, nettoyage au remplacement/reset/démontage et aperçu issu de l'image décodée. « Aucune persistance applicative des images » n'est pas une garantie de non-conservation chez le fournisseur ou dans les logs d'hébergement.

## Tests exécutés

- `npm run typecheck` : réussi.
- `npm run build` : réussi, Next.js installé 15.5.25.
- `CI=1 npm run lint </dev/null` : échec, code 1 ; configuration interactive non complétée, aucune validation lint acquise.
- `node --test tests/audit.test.cjs` : 7 tests, 2 réussis, 5 échoués. Les échecs sont des régressions à corriger, pas des tests ignorés. Pas de nouvelle dépendance.
- Réussites : résultat honnête sans prix accepté ; troisième photo refusée avant fournisseur.

## Limites et décisions ouvertes

- Pas de tests navigateur ou appareil réel, de photos privées, de fournisseur réel, de quota/réseau réel ou de coût facturé dans cette revue.
- Les essais HEIC de Claude Code ne sont pas remis à zéro ; ils restent rapportés. La garantie « la caméra produit toujours un JPEG » doit être remplacée par une hypothèse à vérifier sur les appareils ciblés. Le code réencode en JPEG après décodage, ce qui est différent du format de capture.
- La limite de deux photos est cohérente côté serveur/client pour l'état livré. L'audit teste cette limite sans transformer ce choix en validation produit définitive.
- Aucun audit juridique des sources, de la conservation fournisseur ou de ses conditions ; à traiter avant pilote. La durée d'un scan seule ne permet pas d'en déduire le coût en euros.
